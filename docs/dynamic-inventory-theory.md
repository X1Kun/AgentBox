## 2. 一个适用于当前代码的库存模型

下面是依据排队模型与代码守恒关系作出的项目推导，不是书中直接给出的公式。

在一个不缩容的观察窗口，令初始 READY 为 B，成功发布到 READY 的新实例数为 S(t)，领取实例数为 D(t)，则：

```text
READY(t) = B + S(t) - D(t)
```

库存能覆盖的是“请求领取先发生、补池稍后完成”的缺口。若某一段请求会产生的领取需求超过同期补充数，增加初始库存有可能减少等待；若已有足够 READY 而执行名额耗尽，更多库存不会解除当前等待。

对于近似稳定、无错误与取消、每任务消费一个全新实例的区间，持续成功率有如下简化容量上界：

```text
X_success <= min(k / E[T_create], C / E[T_slot], 其他资源允许的产出)
```

k 是创建 worker 数，C 是执行名额数，T_slot 包含领取到清理完成。它们都没有随本次 READY 目标调整而增大，且耗时会受争用影响。更大的 B 可以缓冲突发，但不能绕过这些上限。旧正文第 4.2 节已给出更完整的近似模型。

Little 定律 L=λW 可以约束同一人口和边界内的平均在途数，不能据此直接断定“最优 READY=λ×创建耗时”。READY 是未消费库存，创建中、执行中与排队者的统计边界不同；最优库存还取决于突发、提前量、资源成本及等待目标。[B07]

空闲回收则是在保留成本和重新准备成本之间取舍。例如在已知下一次需求间隔 d、且两种成本已换算到同一尺度的简化模型里，保留成本为 h×d，销毁后重建成本为 c；h×d>c 时回收可能更合算。但实际 d 未知，还需计入下一次请求的等待损失，因此该模型不能替我们推导出默认 30 秒，也不能证明任意低频负载都节省资源。

## 3. 现有数据证明的是预热价值，尚未证明动态规则价值

只读复算 `artifacts/benchmark-kvm-jXmIUnDF/requests.csv`，使用成功且确认清理的请求及 nearest-rank P50，得到：

| 历史场景 | cold | 固定 warm |
| --- | --- | --- |
| 库存充足：成功请求 wall P50 | 287.776 ms | 156.398 ms |
| 库存充足：setup P50 | 72.567 ms | 10.241 ms |
| 约六秒 steady：成功数 / 发起数 | 49/60 | 34/60 |

这批是 2026-10-15 的 KVM、固定 warm 与旧版本环境，不是当前动态库存对照。它支持“预先准备在命中时能降低等待”的工程方向，也提醒我们“准备得更多”和“长期产出更高”不是一回事。不能用这些数字为新扩容规则背书，不能拿独立阶段 P50 相加减归因。[E02]

历史同批次空闲 warm 父组 memory.current 为 104108032 字节，说明保留库存有真实内存收费。但不能简单除以三个实例、再据此宣称从 3 缩到 1 会精确节约多少内存。

当前短真实用例验证了目标 1→2→1、执行成功及销毁无残留。它证明控制和生命周期路径可用，没有比较动态/固定模式的请求等待或内存时间积分。[动态库存验证记录](dynamic-inventory.md#本轮验证记录)

## 4. 当前扩容规则的两个确定性反例

检查在 `/tmp` 的源码副本中进行，副本与当前 inventory/scheduler/pool/config/engine 哈希一致。调用实际生产方法，使用构造的可达状态与逻辑时间；补池成功由检查代码提供，不运行 runsc，也不把结果当作性能成绩。两例合计 Go 包报告 0.004 秒。[E04]

### 反例 A：执行名额不足，被当成库存不足

构造：执行并发 1，已有 1 个任务占用名额，READY 有 2 个，当前目标 2，另有 1 个请求排队。队列等待的是执行名额。

实际策略结果：

```text
ready=2 executing=1 execution_limit=1 queued=1
target_before=2 target_after=3
```

原因：[scheduler.go](../internal/sandbox/scheduler.go) 的入队路径无条件记录库存需求；[inventory.go](../internal/sandbox/inventory.go) 又把任意非空 waiters 视为扩容信号。两个条件都没有区分队列阻塞原因。增加一个 READY 不能让该排队请求越过被占满的执行名额，也不能从当前状态推断未来一定需要第三个库存。

这与已有[理论正文第 4.3 节](performance-theory.md#43-库存问题的可检验预测)中“idle>0、executing 达到 C 时，修改 B 不解除瓶颈”的判断一致。

### 反例 B：没有库存等待，稀疏请求仍把目标推满

构造：最小目标 1、最大目标 3、动作间隔 1 秒、空闲阈值 30 秒；每 10 秒一个短请求。每个请求都立即取得 READY，且替代实例在决策前已经补好。无排队、无未完成任务。

实际策略结果：

```text
request=1 ready_before_decision=1 queued=0 executing=0 target: 1→2
request=2 ready_before_decision=2 queued=0 executing=0 target: 2→3
request=3 ready_before_decision=3 queued=0 executing=0 target: 3→3
```

原因：领取后会瞬间使 READY＋CREATING 低于目标，Demand 被记住，补齐后也不会撤销；每 10 秒的新活动又打断 30 秒连续空闲。因此在这些条件持续时，虽然 1 个备用实例已够用，策略也会长期维持最大目标。它有界、可执行，但没有识别出“补货已完成、无需提高库存”的情况。

这也解释了为什么“remembered demand”能避免漏掉短任务，却同时放大了误判。书中关于过量供给的警告支持检查这类行为，而不是证明这条规则合理。[B28]

另一个时间边界：默认排队预算 100ms、动作间隔 1s。策略有事件唤醒，不能说所有动作都要等待 1s；但突发若落在冷却期，剩余冷却时间加创建时间可能超过排队预算。反馈动作无法保证挽救触发它的那一波请求。

## 5. 对当前 diff 的判断及最小修正方向

| 部分 | 判断 |
| --- | --- |
| 有界目标、固定执行并发、总容量覆盖 DESTROYING | 保留，明确资源边界与生命周期约束。 |
| 只回收 READY、失败保留记录并停止接单、关闭等待清理 | 保留，是安全回收与资源效率的必要基础。 |
| 压力暂停、动作间隔与空闲滞回 | 保留为保护机制；参数属于可配置工程起点，没有最优性或稳定性证明。 |
| 任意入队即库存需求 | 收紧，需要区分名额等待、库存等待及两者同时不足。 |
| 一次正常消费即保留扩容需求 | 收紧，正常补货缺口与持续/重复库存不足应分开；补货完成后不应仅凭旧消费继续增长。 |
| 动态模式比固定模式性能更好 | 当前证据不足，暂不作此结论。 |

建议下一次实现直接修正信号，复用现有执行中数量、READY、creating 和目标值，避免增加复杂预测系统。至少覆盖两个反例：已有 READY 且仅名额不足不推动扩容；低频、补池及时且无库存等待时不被推到最大。正例则是有实际库存阻塞、增加备用量能覆盖后续供给缺口的短场景，同时保留现有压力、容量、关闭和失败回归。

这些修改可以通过少量确定性用例和一个短集成验证，不需要先开展长时间参数扫描。若要进一步宣称延迟或内存收益，再用一个事先选定的固定库存基线，比较同一请求序列的库存等待、完成/拒绝数与空闲库存时间积分；实例数时间积分是资源代理量，不能自动等同于字节时间积分。书中的 §2.8.1 同时允许基于观测与基于对照的收益分析，没有要求开发前先做大规模实验。[B30]

最终定位：当前 diff 提供了有用的可回收库存管理机制；扩容启发式尚需收紧。书中原理帮助判断哪些机制值得保留、哪些触发条件不成立，而不能把当前实现整体认证为有效的性能优化。
