# 路线图与阶段验收

更新：2026-11-05｜路线：成熟平台主体＋Go 产品适配＋一个可验证的资源策略。架构以 [DESIGN](../DESIGN.md)为准。

在现有 AgentBox 内演进，优先复用 Agent Sandbox 管理会话，Job/Kueue 管理批任务，共用 containerd/gVisor。agentboxd/旧 Gateway 已退出活动源码，不再提供本地运行后端；两类 Kubernetes 工作负载不等于长期维护新旧双后端。

## 1. 当前状态与总体顺序

当前按“先补齐功能，再统一评估和优化”推进，功能范围先限定为本路线图 P0–P4 的既定交付。功能正确性、身份与资源边界、取消/恢复/清理以及故障验收随开发完成；容量标定、收益对照、阈值调优与性能改进集中到功能收尾之后。P3 的 R 标定尚未通过，不阻塞 P4 控制器编码及受控功能验收，也不因此宣称 P3/P4 的性能验收已经完成。P5 保持证据驱动的可选研究，不自动扩入本轮功能范围。

已实现 kind/containerd 普通 Job 功能入口，支持版本锁、预检、独立 kubeconfig、归属保护和结果/清理验收。三次实测闭环见[平台记录](validation.md#platform-bootstrap)。已增加 gVisor 运行时与独立 Calico NetworkPolicy 实验入口；已增加 Agent Sandbox 冷会话与 Go SDK 验收入口；新增固定预热池行为入口；新增生命周期、执行与文件 API；MCP/Agent v2 新链路及源码/系统旧安装退役已完成。P3a 新增 Kueue 固定配额批任务安装与生命周期验收；P3b 已增加真实图片任务、独立产物和 Go 批任务接口；P3c 已增加连续观测入口；P4 健康 AdmissionCheck 功能已实现，R/B/A 性能资格仍未完成。

| 阶段 | 主要交付 | 进入下一阶段的条件 |
| --- | --- | --- |
| P0：功能底座收尾 | 当前 kind 普通 Job 基线与证据 | 功能变更可独立提交；不计为沙箱能力 |
| P1：真实沙箱会话 | gVisor、上游 Agent Sandbox、冷创建与固定预热池 | 执行、文件、身份、超时和回收闭环通过 |
| P2：Go 产品接入与退役 | 会话 API/MCP、调用方切换、移除旧 Daemon | 无 agentboxd 的产品闭环和故障验收通过 |
| P3：有限批任务 | Job/Kueue、固定图片数据集、产物契约、完整观测 | 功能及故障正确性通过后即可开发 P4；R/B 性能资格单独验收 |
| P4：一个准入扩展 | 健康 AdmissionCheck、部署与功能/故障闭环 | 功能完成后统一进行 R/B/A 对照，形成收益与代价结论 |
| P5：证据驱动的后续研究 | 可选原生 Koordinator，或一个明确的上游缺口 | 有在途干扰或其他可复现瓶颈才启动 |

静态资源和锁文件现已整理为 YAML＋Kustomize；Python 保留实验编排。格式迁移不升级组件或重建健康集群，部署与缓存复用须通过精确等价及原 UID/归属检查。

不承诺固定天数，不同时堆叠多种控制机制。功能正确、测量有效、性能收益分别验收；负向性能结论可以完成研究阶段。新能力实现前不增加虚构命令或空模块。

## 3. P1：真实 gVisor 与上游会话

运行时子步骤提供固定发布包、官方 shim/RuntimeClass、运行身份/资源与终止回收验证，见[验收记录](validation.md#gvisor-runtime)。另有显式新建的 Calico 网络策略 profile，验证范围见[网络记录](validation.md#network-policy)。冷会话子步骤固定上游 v1.0.8，使用同版本 sandboxd/Go SDK 和 replicas=0 的池进行冷分配，独立入口见[运维指南](operations.md#cold-sessions)，13 项真实行为检查与清理已通过，见[验收记录](validation.md#cold-sessions)。固定预热池子步骤新增 `warm` profile（库存目标 2、总 Pod quota 3），用于验证并发领取、补充、耗尽与恢复；九项真实行为与清理已通过，包含配额耗尽后的失败回滚、库存恢复和再次领取干净环境，见[验收记录](validation.md#warm-pool)。操作见[固定池入口](operations.md#warm-pool)。完整产品安全边界仍待完成。

本阶段只做行为验收，不安排压测、延迟分位数或资源收益对照；日志耗时仅用于排障。

本次冷会话范围：多次命令和文件保留、双会话隔离、稳定资源身份、失败后继续执行、显式关闭/到期、未知执行不重放及运行中关闭。固定预热供给和配额耗尽已验证，产品鉴权后续独立交付；暂不确定空闲回收或动态容量策略。

本笔提交补充 `fault` 行为 profile：重启本项目上游控制器时保持运行中命令及会话身份；删除指定会话 Pod 后观察新 UID 和工作目录重置，验收器拒绝沿用旧身份且不重放命令；在到期点显式关闭并检查幂等与回收。宿主仅按 UID/归属链操作本次对象，执行客户端权限保持只读关联资源与 Claim 生命周期。八项真实行为检查与 API/CRI/运行时/namespace 清理已通过，见[故障验收](validation.md#session-faults)。终态容器失败的 Retain/Recreate、跨重启持久化和产品级身份防护不由此自动推导。

按顺序实施：

1. 配置 containerd 的官方 runsc handler/RuntimeClass，锁定 runtime、shim、cgroup 和内核组合；先验证一个真实 gVisor Pod，无静默回落。
2. 部署锁定版本的 Agent Sandbox CRD/控制器及必要执行服务/SDK，先冷创建会话，再引入固定大小 WarmPool；只使用一个受控模板。
3. 配置能实际执行 NetworkPolicy 的 CNI、身份与通道权限、资源/输出/工作目录上限。控制器权限不进入任务 Pod。
4. 用直接上游客户端验证多条命令、文件写读、关闭与到期。首版每会话顺序执行，保留文件，不承诺解释器变量或进程快照。
5. 冻结池耗尽与取消行为：有限等待或明确失败；取消无法确认时关闭会话收敛。使用后的会话不得重新作为干净库存分配。
6. 增加必要会话指标和最小监控，分别测量冷创建、预热领取、首条命令、后续命令和清理；暂不研发动态池策略。

验收：

- [ ] 真实 gVisor 隔离、资源与网络边界，跨会话文件不可见，执行凭据不泄露。
- [ ] 池命中/耗尽、并发领取、TTL 与关闭竞争、控制器重启、Pod 失败都可观察。
- [ ] 无重复领取、使用过的环境重新入池或无法解释的残留；超时不误报任务已终止。
- [ ] 安装、检查、回退与限定范围清理可复现；版本变更按上游存储/API 兼容要求处理。

kind 可承担功能验收；若当前宿主无法稳定支持目标 runtime/CNI，则记录阻塞并使用明确的专用测试节点，不用普通 runtime 成功替代。

## 4. P2：Go API/MCP 与 agentboxd 退役

### P2a：薄产品适配

第一笔新增最小 `agentbox-api` 生命周期服务：异步创建、查询、关闭、配置身份、命名 Claim 幂等与持久 UID 绑定。状态依赖上游 Retain Claim，不建第二套生命周期 CRD/状态库；首次 Ready 后的 Pod 替换会失效而不重绑。执行/文件已在第二步补齐，MCP 和实际退役随后完成。本阶段仅做行为验收；受限凭据下的六项真实 API 检查与运行时清理已通过，见[API 验收](validation.md#session-api)。

第二步已增加执行/文件适配：按原身份连接上游 sandboxd、Claim CAS 数据操作互斥、有界结果、超时/未知结果关闭。七项真实 API 行为检查、四个运行时的独立回收及完整 `make check` 已通过，见[执行验收](validation.md#session-execution)；不增加性能实验。另新增 closed_at 持久观察和独立管理员记录清理入口，默认预览，按保留期及原 UID/resourceVersion 删除，元数据配额/回收验收独立于执行运行时。本轮合并为一个交付：MCP/Agent v2 链路、默认入口切换和旧源码/系统安装退役；行为与清理验证作为共同门槛。开发期复用健康集群，测试后只清本次资源。

复用现有 Agent、模型客户端和 MCP 通用能力，使用上游 Go 客户端/执行协议承接会话创建、查询、命令执行、文件访问和关闭。产品只做身份/授权、稳定关联、受控模板、有限预算与结果适配；不新建池控制器、Node Agent、宿主执行器或通用会话 CRD。

按[使用契约](usage.md#target)定义新版本工具，区分会话期限、命令超时、调用等待与清理预算。模型 key 留在 Agent，执行 Pod 不得到集群权限。首版不做用户管理 SaaS，但身份与资源归属必须可验证。

### P2b：调用链与故障验收

至少覆盖：创建响应丢失后的同对象查询、命令未知结果不重放、同会话并发冲突、超时后的执行收敛、关闭后拒绝命令、路径越界和输出超限。无法查询未知命令结果时明确返回 unknown 并关闭会话，不新增任务日志数据库来伪造执行一次保证。

已在没有运行 agentboxd/旧 Gateway 时，通过 Agent → stdio MCP v2 → Go 产品层 → 真实会话 → 结果闭环；包含确定性模型修正、文件下载、超时及成功执行响应丢失后不重放。用确定性模型替身完成自动回归，付费模型仅作显式演示。旧 execute_python 不静默获得跨调用状态或新取消语义。

<a id="retirement"></a>
### P2c：切换与退役（本轮完成）

会话平台和新接口独立验收后即可退役，P3 批任务、P4 策略与 P5 Koordinator 不作为前置条件。下列门槛已经本轮代码清退、真实链路与管理员退役记录核对，复现见[运维流程](operations.md#retirement)：

1. 固定旧源码/构建版本，盘点调用方、服务、配置、凭据、实例与状态归属。
2. 切换调用方并关闭旧入口新提交；排空或明确取消旧任务，不自动迁入会话/Job。
3. 核对进程、bundle、cgroup 回收；无法确认时保留现场处理，不宣告完成。
4. 停止并移除旧配对服务、监听和凭据分发，保护新平台或其他服务共用的依赖。
5. 从活动构建/CI/发布中清退 agentboxd、本地 runsc 适配、FIFO/Warm/AIMD 和专用 Unix Gateway；保留可复用校验与历史版本。
6. 默认文档改为新产品入口。回退仅通过明确人工版本发布，不做请求级自动回落。

完成标准：新会话执行只走目标平台，旧工作无未解释残留，默认安装/构建不依赖 Daemon，旧证据仍可复现。上游执行服务、kubelet/containerd 的存在不影响自研 Daemon 的退役判断。

## 5. P3：批任务、产物和静态基线

P3a 提供固定 Kueue v0.20.3 的受限安装、LocalQueue/ClusterQueue/Worker ResourceFlavor 与 gVisor Job 验收；队列和本轮 namespace/配额临时创建，正常测试后清理，Kueue 及健康集群保留。固定 CPU 计算验证排队、准入、排队/运行取消、超配额、执行失败和 deadline；这是功能底座，不代表图片批处理产品或性能基线完成。操作见[批任务运维](operations.md#batch)，结果见[批任务验收](validation.md#batch)。

P3b 将固定图片数据集、独立产物契约和 Go 批任务接口合并交付：四张公开图片和处理库/wheel 固定版本/摘要；真实缩略图/灰度处理在 gVisor Job 内运行；独立 PVC 保留产物与有限幂等记录；支持原 Job UID 查询/取消、跨身份拒绝、重启后恢复、失败尝试隔离及已验证 PNG 下载。接口见[使用指南](usage.md#batch-api)，准备和验收见[运维指南](operations.md#batch-images)。

P3c 分为观测/实验能力和性能证据两部分：API 指标、只读 Kubernetes/运行时观察器、本地 Prometheus/Grafana、固定轨迹与缺失/恢复验收作为功能能力补齐；R 容量标定、静态批配额 B 扫描留到统一性能阶段。当前采集功能不构成 R/B 成绩，也不证明所有 gVisor 叶资源均可由 cAdvisor 测得，边界见[观测验收](validation.md#observability)。P4 功能开发不再等待这些性能成绩；P3b 的功能结果不作为性能收益或磁盘问题根治证据。

已补充固定到达驱动、多 Pod/真实用户行为矩阵、请求链路日志与清理错误回归；这些准备不等于正式容量成绩。R/B 编排现提供 `make platform-static-baseline`：冻结 YAML 输入，从低到高逐档进行五轮 R 标定；达到预定质量目标的有效轨迹，才允许引用原报告进入 R/B1/B2 交错对照。每组保留逐请求账本、图片产物校验、积压与窗口外 drain，入口见[基线运维](operations.md#static-baseline)。该资格门槛继续用于正式性能对照，不再作为 P4 功能开发前置。

当前 R 实测尚未形成合格档位：最低档前三轮未达到 3s/95% 的预设实验目标，第四轮因 inventory 观测失效停止；本轮资源已回收，正式 B 对照门槛保持关闭。尾延迟定位和重复 R 标定转入后续性能阶段；影响功能正确性或故障恢复的问题仍及时修复。不能把既有负向结果写成 P3/P4 已完成，详见[静态基线验收](validation.md#static-baseline)。

已补充 domain/source 独立预算、逐读取原因/耗时、sandboxd 八阶段关联、宿主与控制面时序及失败归档，诊断入口为 `make platform-diagnostics-test`。真实权限故障验收独立于 R 容量资格；新日志不能倒推此前已回收轮次的细分根因，范围见[诊断细节验收](validation.md#diagnostic-details)。

宿主脚本与容器/Pod 程序已按执行职责分离，平台安装、产品准备、验收和实验边界由回归约束；CLI 使用按命令加载。该结构重构已通过完整产品、冷 SDK 和诊断验收，原集群/runtime 身份保持，范围见[脚本重构验收](validation.md#script-layout)。它不替代尚未完成的 R/B 性能标定。

容量实验前先补齐维护与分层：后台 reconcile 独立于 readiness，统一快照新鲜度/退出失效，修正自然到期观测、提交锁范围及分页进度；抽离轻量 DTO/工具契约并拆分相关职责。验证入口为 `make platform-maintenance-test`，边界见[维护验收](validation.md#maintenance)。记录容量回收先按[后续契约](usage.md#batch-record-evolution)设计，当前 v2 不自动删记录；该有限容量平台不作为长期连续运行已经完成的证明。

会话相关适配器已聚合到 `internal/session/` 的 protocol/httpapi/client/sandboxd 子包，业务主包按文件拆职责；单一 smoke 命令使用的验收场景回到命令目录。包边界和依赖方向继续由回归检查，已有运行时与当前验收客户端分别验证，见[目录整理验收](validation.md#session-layout)。

先完成 Job/Kueue 的 LocalQueue/ClusterQueue/ResourceFlavor，固定规格与配额，不借用、不抢占。会话 namespace/固定池预算与批任务预算分开声明，共同受 Worker 实际容量约束；首版不让 Kueue 接管 Claim 或命令。

交付：

- 一份固定图片 manifest 与预装处理库，明确线程数、输入/输出容量、存储机制与校验。
- Go 产品层增加受控批任务提交/查询/取消和产物引用；保持与会话工具分离，不开放任意 PodSpec。
- 提交标识/输入冲突、Job/Pod attempt、重复输出发布、断线后继续、取消与 TTL 语义可解释。
- 补齐 Prometheus/Grafana 与固定压测轨迹。现有 Mock Core 仅作辅助诊断，正式交互质量来自真实会话命令。
- 批计算实际在 Job Pod 内执行；不把 Job 作为远程沙箱客户端而漏算计算资源。

验收：批任务等待、准入、执行失败、重试、结果校验与回收通过；先在 R 组标定会话容量，再扫描 B 组静态批配额。每组使用相同固定预热池、模板与预算口径，记录完整任务清单和积压。

## 6. P4：健康感知批任务准入

P4 已增加健康信号读取与有效性判断、状态机/滞回/放行节奏、Kueue 状态写入、重启恢复，以及独立部署、最小权限、日志和指标。功能验收使用显式、可控的健康/失效样本与锁定版本的真实 Kueue；R 基线未通过不阻止这些验收。未标定的测试参数不能作为已验证部署默认值，也不自动将扩展挂到现有产品队列。功能闭环完成后，再与 P3 的 R/B 一起进行性能验收。

按[AdmissionCheck 设计](admission-check.md)使用 Go/controller-runtime 与官方扩展协议。只管理本检查项，不写 Job suspend、不改池规模、不直接写 cgroup，不因交互恶化撤销已准入任务。

必须交付：样本过期/不足处理、滞回、恢复节奏、Pending 占配额处置、UID/resourceVersion 冲突保护、重启/leader 切换恢复、最小 RBAC、决策日志与指标。

确定性单元测试、API 竞态和真实 Kueue 故障验证分别完成。正式比较 B/A 时保持池规模、会话数量/规格、批任务模板、配额、节点、runtime 和负载一致；同时报告交互及时成功、批任务等待/完成、空闲资源和控制成本。指标丢失不能被当成空闲，长期饿死批任务不算收益。

形成可复现的正向或负向结论即可完成；静态策略已经足够时，扩展可以保留为可选，不为了证明研发价值放宽 SLO 或更换对手。

### 6.2 按依赖顺序的五项功能交付

以下五项功能均已有对应实现、回归和部署入口。功能验收与性能资格分别记录，不将样例参数提升为已标定默认值。

| 顺序 | 交付内容与代码落点 | 完成标准 |
| --- | --- | --- |
| P4a：健康样本与查询 | 在 `internal/admission/` 及其 `health` 子包定义配置、健康样本和 Prometheus 读取边界；在现有 Go 实验驱动及观测配置中增加受控命令的在线窗口导出 | 固定健康域、命令类型、后续命令口径、SLO、样本量、原始采样时间和配置版本；正确及时数与全部计划请求逐条对账；过期、空值、缺测、重置、查询失败及配置不匹配均不可发许可 |
| P4b：纯决策状态机 | 在准入包中实现 Unknown/HealthyPending/Healthy/Protect/Degraded、滞回、稳定窗口、放行间隔及最长等待决策；与网络和 Kubernetes 写入分离 | 注入时钟和样本，验证非均匀时间间隔、重复/倒序/未来样本、低样本量、持续恶化与恢复、配置切换；反复读取同一旧样本不能积累成新健康证据 |
| P4c：Kueue 适配与写入保护 | 增加独立 `cmd/agentbox-admission`，使用 controller-runtime 管理 AdmissionCheck Active 与本检查项的 Workload 状态 | 只处理显式配置范围；写入前重读 UID/resourceVersion、配额与 Admitted 状态，冲突重判；保留其他检查项；Pending 超时仅对未准入对象按锁定协议 Retry；API 集成测试证明竞态不会误驱逐在途任务 |
| P4d：许可节奏与接管恢复 | 实现健康域内串行发放、leader election、持久状态重建、健康窗口重建及有界故障行为 | 多个待放行对象不能同时消费一个间隔；覆盖写成功但响应丢失、进程重启、leader 切换、UID 重建和配置切换；用故障测试确定接管窗口的许可上界，恢复后无集中放行 |
| P4e：部署与真实故障闭环 | 独立准入部署组件及完整渲染器；扩展 `scripts/lib/acceptance/` 和 `tests/scripts/`，复用平台夹具、复用真实图片产品客户端和原归属保护 | 独立身份、最小 RBAC、配置校验、查询网络边界、有限标签指标和决策 JSONL；通过真实 Kueue/Job/gVisor 故障矩阵，验证图片产物及 API/CRI/进程回收；记录启用、停收、排空和卸载流程 |

P4a 先确定信号生产者：首版由可信的固定到达驱动验证真实会话输出并发布窗口，Controller 只查询管理员指定的 Prometheus，不执行用户代码。窗口结束前尚未到截止的请求不能提前计为失败或漏掉；已过截止的拒绝、超时、错误和未完成请求必须进入相应窗口的分母。低流量及有效零请求仍按最小样本量处理；生成器未维持轨迹时显式标记无效，不作为空闲放行。该受控信号不能外推为任意用户程序的正确性证明。

P4c 的 API 集成测试应使用真实 API Server/CRD 状态子资源校验 UID/resourceVersion 冲突；fake client 单独通过不能证明服务端并发语义。P4d 对跨对象许可和 leader 切换的保证须明确边界，不把 Lease 当作跨对象原子事务。P4e 对受控信号注入的故障验证和真实会话信号联通分别留证，测试阈值不升级为已标定默认值。

真实功能验收至少覆盖：不健康/样本不足保持 Pending；健康持续后逐个 Ready；未准入长等待 Retry 并观察配额释放和退避；指标失联/陈旧、查询或状态写入权限拒绝；Controller 重启/leader 切换；Workload 同名 UID 替换；已有其他检查项；Ready 后健康恶化及接近 Admitted 的竞态；取消/终态及最终回收。已发 Ready 仍可能在 Controller 故障后启动，这一异步窗口须在报告中保留。

### 6.3 功能收尾后的统一评估与维护顺序

1. **先检查测量有效性与尾延迟。** 用已有请求阶段日志、observer、宿主和控制面证据定位新一轮问题；保持身份复核与未知结果不重放。既有机械盘/I/O 现场仅作诊断线索，不直接归因为全部时延根因。
2. **取得新的 R 资格，再扫描 B。** 固定代码/镜像、预热池、资源预算、到达轨迹和质量目标，每档至少五轮有效测量；质量未达标是有效负向结果，观测/生成器失效则停止。原负向记录保留，不通过放宽目标使其变为合格。
3. **冻结静态候选后扩展到 A。** 现有 `results.py` 只接受 R/B1/B2，届时显式扩展实验 schema、计划、资格校验和容量预算，记录健康样本、Ready→Admitted→启动、全部批任务等待与积压。先用调参集选择参数，再在独立正式轨迹中配对、交错运行，控制其他输入和采集开销一致。
4. **按结果决定后续。** 同时评价会话正确及时成功、经校验的批产出、等待/饥饿、预热空闲和控制成本。只有在途干扰有可复现证据时进入 P5；批记录长期回收、动态池、多节点和公平性分别立项，不扩入当前 P4 功能提交。

已随功能实现同步纠正文档现状：`usage.md` 明确批 HTTP API 已实现而 MCP 仍仅提供会话工具；`runtime.md` 区分已接入批任务的 Kueue 与会话；`operations.md` 清退旧 Makefile 入口说明。历史 JSON 与原始失败报告保持不变。

## 7. P5：根据证据选择后续研究

仅在在途任务竞争成为明确瓶颈时，先评价原生 Koordinator CPU Suppress。确认 cgroup、containerd/gVisor、BE/LS、batch 扩展资源及 Kueue 单位一致，再补 B/A/K/AK 四组；如资源模型变化，重新建立共同基线。

动态预热、公平性、节点策略只选一个有证据的方向继续。若以后研究中心转为 Firecracker 快照/恢复，可独立搭建 E2B 对照实验，不把裸 VMM 自研运行管理塞回 AgentBox 主线。

## 8. 统一交付规则

- 保持现有文档层级：根 README/DESIGN＋六份主文档；不为每个候选组件新增说明书。
