# 路线图与阶段验收

更新：2026-10-28｜路线：成熟平台主体＋Go 产品适配＋一个可验证的资源策略。架构以 [DESIGN](../DESIGN.md)为准。

在现有 AgentBox 内演进，优先复用 Agent Sandbox 管理会话，Job/Kueue 管理批任务，共用 containerd/gVisor。agentboxd 进入退役，不扩展本地运行后端；两类 Kubernetes 工作负载不等于长期维护新旧双后端。

## 1. 当前状态与总体顺序

已实现 kind/containerd 普通 Job 功能入口，支持版本锁、预检、独立 kubeconfig、归属保护和结果/清理验收。三次实测闭环见[平台记录](validation.md#platform-bootstrap)。已增加 gVisor 运行时与独立 Calico NetworkPolicy 实验入口；已增加 Agent Sandbox 冷会话与 Go SDK 验收入口；新增固定预热池行为入口；Kueue、真实图片任务、新 API/MCP、AdmissionCheck 与实际退役仍未完成。

| 阶段 | 主要交付 | 进入下一阶段的条件 |
| --- | --- | --- |
| P0：功能底座收尾 | 当前 kind 普通 Job 基线与证据 | 功能变更可独立提交；不计为沙箱能力 |
| P1：真实沙箱会话 | gVisor、上游 Agent Sandbox、冷创建与固定预热池 | 执行、文件、身份、超时和回收闭环通过 |
| P2：Go 产品接入与退役 | 会话 API/MCP、调用方切换、移除旧 Daemon | 无 agentboxd 的产品闭环和故障验收通过 |
| P3：有限批任务 | Job/Kueue、固定图片数据集、产物契约、完整观测 | R/B 静态基线及批任务故障正确性通过 |
| P4：一个准入扩展 | 保护交互质量的健康 AdmissionCheck | 同池规模/预算的 B/A 对照，形成收益与代价结论 |
| P5：证据驱动的后续研究 | 可选原生 Koordinator，或一个明确的上游缺口 | 有在途干扰或其他可复现瓶颈才启动 |

不承诺固定天数，不同时堆叠多种控制机制。功能正确、测量有效、性能收益分别验收；负向性能结论可以完成研究阶段。新能力实现前不增加虚构命令或空模块。

- [x] 独立集群/context、归属保护、有限超时、失败诊断与清理。
- [x] 可信普通 Job 在专用 worker 计算固定结果，核对 Pod 与最终回收。

- [x] 普通功能基线已通过 PR #13 合并（9cd1b2c）；后续改造按独立验收项推进。

本阶段脚本只做实验编排；不承担常驻任务服务。后续组件的版本兼容、CNI 策略和生产环境条件不由普通 Job 验收替代。

## 3. P1：真实 gVisor 与上游会话

运行时子步骤提供固定发布包、官方 shim/RuntimeClass、运行身份/资源与终止回收验证，见[验收记录](validation.md#gvisor-runtime)。另有显式新建的 Calico 网络策略 profile，验证范围见[网络记录](validation.md#network-policy)。冷会话子步骤固定上游 v1.0.8，使用同版本 sandboxd/Go SDK 和 replicas=0 的池进行冷分配，独立入口见[运维指南](operations.md#cold-sessions)，13 项真实行为检查与清理已通过，见[验收记录](validation.md#cold-sessions)。固定预热池子步骤新增 `warm` profile（库存目标 2、总 Pod quota 3），用于验证并发领取、补充、耗尽与恢复；九项真实行为与清理已通过，包含配额耗尽后的失败回滚、库存恢复和再次领取干净环境，见[验收记录](validation.md#warm-pool)。操作见[固定池入口](operations.md#warm-pool)。完整产品安全边界仍待完成。

本阶段只做行为验收，不安排压测、延迟分位数或资源收益对照；日志耗时仅用于排障。

本次冷会话范围：多次命令和文件保留、双会话隔离、稳定资源身份、失败后继续执行、显式关闭/到期、未知执行不重放及运行中关闭。固定预热供给和配额耗尽作为下一子步骤验证，产品鉴权后续独立交付；暂不确定空闲回收或动态容量策略。

按顺序实施：

1. 配置 containerd 的官方 runsc handler/RuntimeClass，锁定 runtime、shim、cgroup 和内核组合；先验证一个真实 gVisor Pod，无静默回落。
2. 部署锁定版本的 Agent Sandbox CRD/控制器及必要执行服务/SDK，先冷创建会话，再引入固定大小 WarmPool；只使用一个受控模板。
3. 配置能实际执行 NetworkPolicy 的 CNI、身份与通道权限、资源/输出/工作目录上限。控制器权限不进入任务 Pod。
4. 用直接上游客户端验证多条命令、文件写读、关闭与到期。首版每会话顺序执行，保留文件，不承诺解释器变量或进程快照。
5. 冻结池耗尽与取消行为：有限等待或明确失败；取消无法确认时关闭会话收敛。使用后的会话不得重新作为干净库存分配。
6. 增加必要会话指标和最小监控，分别测量冷创建、预热领取、首条命令、后续命令和清理；暂不研发动态池策略。

验收：

- [ ] 真实 gVisor 隔离、资源与网络边界，跨会话文件不可见，执行凭据不泄露。
- [ ] 池命中/耗尽、并发领取、TTL 与关闭竞争、控制器重启、Pod 失败都可观察。
- [ ] 无重复领取、使用过的环境重新入池或无法解释的残留；超时不误报任务已终止。
- [ ] 安装、检查、回退与限定范围清理可复现；版本变更按上游存储/API 兼容要求处理。

kind 可承担功能验收；若当前宿主无法稳定支持目标 runtime/CNI，则记录阻塞并使用明确的专用测试节点，不用普通 runtime 成功替代。

## 4. P2：Go API/MCP 与 agentboxd 退役

### P2a：薄产品适配

复用现有 Agent、模型客户端和 MCP 通用能力，使用上游 Go 客户端/执行协议承接会话创建、查询、命令执行、文件访问和关闭。产品只做身份/授权、稳定关联、受控模板、有限预算与结果适配；不新建池控制器、Node Agent、宿主执行器或通用会话 CRD。

按[使用契约](usage.md#target)定义新版本工具，区分会话期限、命令超时、调用等待与清理预算。模型 key 留在 Agent，执行 Pod 不得到集群权限。首版不做用户管理 SaaS，但身份与资源归属必须可验证。

### P2b：调用链与故障验收

至少覆盖：创建响应丢失后的同对象查询、命令未知结果不重放、同会话并发冲突、超时后的执行收敛、关闭后拒绝命令、路径越界和输出超限。无法查询未知命令结果时明确返回 unknown 并关闭会话，不新增任务日志数据库来伪造执行一次保证。

没有运行 agentboxd/旧 Gateway 时，Agent → MCP → Go 产品层 → 真实会话 → 结果闭环通过。用确定性模型替身完成自动回归，付费模型仅作显式演示。旧 execute_python 不静默获得跨调用状态或新取消语义。

<a id="retirement"></a>
### P2c：切换与退役

会话平台和新接口独立验收后即可退役，P3 批任务、P4 策略与 P5 Koordinator 不作为前置条件。按[运维流程](operations.md#retirement)：

1. 固定旧源码/构建版本，盘点调用方、服务、配置、凭据、实例与状态归属。
2. 切换调用方并关闭旧入口新提交；排空或明确取消旧任务，不自动迁入会话/Job。
3. 核对进程、bundle、cgroup 回收；无法确认时保留现场处理，不宣告完成。
4. 停止并移除旧配对服务、监听和凭据分发，保护新平台或其他服务共用的依赖。
5. 从活动构建/CI/发布中清退 agentboxd、本地 runsc 适配、FIFO/Warm/AIMD 和专用 Unix Gateway；保留可复用校验与历史版本。
6. 默认文档改为新产品入口。回退仅通过明确人工版本发布，不做请求级自动回落。

完成标准：新会话执行只走目标平台，旧工作无未解释残留，默认安装/构建不依赖 Daemon，旧证据仍可复现。上游执行服务、kubelet/containerd 的存在不影响自研 Daemon 的退役判断。

## 5. P3：批任务、产物和静态基线

先完成 Job/Kueue 的 LocalQueue/ClusterQueue/ResourceFlavor，固定规格与配额，不借用、不抢占。会话 namespace/固定池预算与批任务预算分开声明，共同受 Worker 实际容量约束；首版不让 Kueue 接管 Claim 或命令。

交付：

- 一份固定图片 manifest 与预装处理库，明确线程数、输入/输出容量、存储机制与校验。
- Go 产品层增加受控批任务提交/查询/取消和产物引用；保持与会话工具分离，不开放任意 PodSpec。
- 提交标识/输入冲突、Job/Pod attempt、重复输出发布、断线后继续、取消与 TTL 语义可解释。
- 补齐 Prometheus/Grafana 与固定压测轨迹。现有 Mock Core 仅作辅助诊断，正式交互质量来自真实会话命令。
- 批计算实际在 Job Pod 内执行；不把 Job 作为远程沙箱客户端而漏算计算资源。

验收：批任务等待、准入、执行失败、重试、结果校验与回收通过；先在 R 组标定会话容量，再扫描 B 组静态批配额。每组使用相同固定预热池、模板与预算口径，记录完整任务清单和积压。

## 6. P4：健康感知批任务准入

按[AdmissionCheck 设计](admission-check.md)使用 Go/controller-runtime 与官方扩展协议。只管理本检查项，不写 Job suspend、不改池规模、不直接写 cgroup，不因交互恶化撤销已准入任务。

必须交付：样本过期/不足处理、滞回、恢复节奏、Pending 占配额处置、UID/resourceVersion 冲突保护、重启/leader 切换恢复、最小 RBAC、决策日志与指标。

确定性单元测试、API 竞态和真实 Kueue 故障验证分别完成。正式比较 B/A 时保持池规模、会话数量/规格、批任务模板、配额、节点、runtime 和负载一致；同时报告交互及时成功、批任务等待/完成、空闲资源和控制成本。指标丢失不能被当成空闲，长期饿死批任务不算收益。

形成可复现的正向或负向结论即可完成；静态策略已经足够时，扩展可以保留为可选，不为了证明研发价值放宽 SLO 或更换对手。

## 7. P5：根据证据选择后续研究

仅在在途任务竞争成为明确瓶颈时，先评价原生 Koordinator CPU Suppress。确认 cgroup、containerd/gVisor、BE/LS、batch 扩展资源及 Kueue 单位一致，再补 B/A/K/AK 四组；如资源模型变化，重新建立共同基线。

动态预热、公平性、节点策略只选一个有证据的方向继续。若以后研究中心转为 Firecracker 快照/恢复，可独立搭建 E2B 对照实验，不把裸 VMM 自研运行管理塞回 AgentBox 主线。

## 8. 统一交付规则

- 保持现有文档层级：根 README/DESIGN＋六份主文档；不为每个候选组件新增说明书。
- 文档明确规划、已实现、已验证和已测收益；命令仅列已有入口。
- 代码按改动跑必要回归；运行时、权限和生命周期变化补真实验收。文档改动检查链接、锚点和内容一致性。
- 保存版本、输入、有效开关和失败轮次；历史数据与新平台分开，kind 不替代生产/物理跨机证据。
- 不同时实现自研 Node Agent、调度器、通用队列/配额账本、多种沙箱控制面或额外 CRD。
- 安装成功不等于生产就绪；发布必须说明容量、身份、隔离、资源归属、失败恢复、结果与清理边界。
