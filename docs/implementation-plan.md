# 后续实现计划

更新日期：2026-10-20。当前单机执行、一次性预热池、CPU AIMD、压力准入与补池门控已有初版。接下来以可用功能交付为主，每阶段只运行与改动直接相关的回归和短流程验证。

## 已完成的审查修复

- 修复 enforce 采样误判；observe/enforce 均保留正常质量统计，不支持的模式仍报告错误。
- 统一 usage 为从实例创建到销毁前采样的累计值，明确后续清理消耗可能未计入。
- 明确 request_id 当前仅用于关联，不提供去重与不确定结果重放保证。
- 更新旧 QoS 文档中的 enforce 和补池门控说明。

上述修复已通过 `make check` 和构建。新增记录器回归先在旧代码上复现，再验证修复后的行为。

## 1. 已实现：有界动态预热库存

交付目标：库存根据请求需求在配置范围内增减，复用现有一次性池、FIFO 和压力门控，完成单机供给管理。

实现内容：

1. 增加显式启用开关、最小 READY 目标、最大 READY 目标和缩容推荐稳定窗口；默认关闭，现有固定库存配置继续有效。
2. 在 pool 中增加独立的库存目标计算逻辑。首版采用简单规则：仅实际库存阻塞推动目标上调；未消费的备用余量经推荐稳定窗口后逐级降低目标。设置动作间隔，避免请求突发时频繁伸缩。
3. refill 根据当前目标补池；压力暂停期间不发起新创建、不提高目标，恢复后继续按目标补充。执行并发保持现有静态配置。
4. 缩容只销毁多余 READY 实例。先在池锁内移出可领取库存并标记 DESTROYING，再执行清理；清理确认前仍占总容量。已领取、执行中和创建中的实例沿用原有生命周期。
5. 状态接口增加当前目标、上下界、调整原因和动作计数；同步 CLI、systemd 环境参数和配置校验。

已接入 `internal/sandbox` 的配置、pool/refill 与状态报告、`internal/api`、daemon 参数及 systemd 配置。具体规则与启用方式见[动态库存](dynamic-inventory.md)。

完成标准：覆盖目标上下界、需求增加、空闲缩容、压力暂停/恢复、关闭竞争和清理失败；验证缩容不误删在途实例、总量守恒、取消和 FIFO 语义保持。用一次短真实 warm 流程验证“补池 → 执行 → 空闲缩容 → 关闭”，无需开展参数扫描或吞吐对照。

本阶段已通过完整 `make check`、构建及一个真实 systrap 短用例（tmpfs 测试依赖），验证结果见[动态库存记录](dynamic-inventory.md#本轮验证记录)。下一项是 Gateway。

[库存控制 v2](inventory-open-source-design.md)的阻塞归因与推荐稳定窗口已实现，替换旧 v1 规则；可选令牌桶留待按需接入。缩容参数已改为 warm-downscale-window，不再要求整个池连续无请求。性能收益另行验证，不作为继续开发的统一前置条件。

## 2. 接着实现：普通用户 Gateway 与本机 daemon 通信

交付目标：形成可由 Agent 客户端使用的普通用户入口，将网络接入与特权运行时操作分开。

实现内容：

1. 让 daemon 支持带文件权限控制的 Unix socket 监听，复用当前 Execute/Status 协议和 HTTP handler，避免首版再引入一套 RPC 编解码。
2. 新增 `agentbox-gateway`，以普通用户运行；提供执行、状态与健康接口，将鉴权后的请求转发到本机 daemon。
3. 传播请求取消与剩余期限，保留拒绝原因及结构化执行结果。为入口设置请求大小与并发边界，避免增加无界缓冲；连接中断后不自动重放执行请求。
4. 补充单 worker 的安装和配置示例，明确 socket 所有者、组权限及就绪依赖。现有 daemon 的 loopback HTTP 模式继续支持本地开发。

完成标准：验证鉴权、socket 权限、取消传播、daemon 不可用与容量拒绝的映射；完成一次 Gateway → daemon → Python → 清理的短流程。

## 3. 然后实现：MCP 工具接入与 Agent 示例

交付目标：Agent 能通过标准工具调用使用现有沙箱能力。

实现内容：

1. 增加 MCP 适配入口，首版提供 Python 执行与状态查询，调用 Gateway。
2. 工具参数复用现有 runtime/code/stdin/timeout/env 约束，返回结构化状态、输出、耗时与清理结果。
3. 补充凭据配置和错误说明，明确超时、压力拒绝、基础设施失败和不确定结果的处理。
4. 提供最小调用示例，完成“提交代码 → 读取结果 → 根据结果继续调用”的完整演示。

完成标准：验证参数映射、取消和错误传播；跑通成功、代码异常及超时三个短用例。模型本身不作为回归测试依赖。

## 必要验证与已知问题

- 每次改动先运行相关单元/race 测试；一组功能收尾时运行一次 `make check` 和构建。修改沙箱生命周期、权限或传输链路时，增加对应的短真实集成验证。
- 正常磁盘依赖下的历史 create/delete 超时保留为已知问题。与本次改动相关的短流程若复现，就按阶段日志定位并修复；设备或权限不足时标明未验证。它不作为开展全部后续开发前必须完成的跨平台实验项目。
- 长时间 cold/warm 供给测试、动态 QoS 四组对照和参数寻优列为可选性能工作，需要性能报告或优化决策时再做；不作为上述功能实现的前置条件。动态 QoS 的性能收益仍标记为未证实。
- 解释器预加载、动态执行并发、内存压力准入、多租户和多节点另行排期；本轮计划先交付动态库存、Gateway 和 MCP 三项能力。
