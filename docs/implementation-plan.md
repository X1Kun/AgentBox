## 本轮优先：单机可靠性与供给收敛

1. 已实现清理独立预算、内存部署校验和启动探测。超时前关联进程栈、挂载和设备计数；普通磁盘底层原因尚未根治。
2. 已统一 Cold/Warm 创建与 FIFO；后台补池在执行槽饱和或队列非空时退让，按需创建保持有界。短测保留原始完成数和拒绝，不保证长期吞吐。
3. 已完成原 AIMD 对照和无沙箱核心业务独立基线；新增可选的业务健康约束与额度借用。基线通过不等于某个配额已校准，新模式尚无业务性能对照，保持默认关闭。

本轮结果见 [验收记录](validation.md)。面试讲解使用 [证据边界明确的版本](interview.md)。

## 已补充：交互式波次与预热收益

新增同轨迹 waves 基准，按 5 请求/1 秒、空闲 10 秒、20 请求/5 秒、空闲 10 秒重复。到达时间预先确定，运行期间不强制等库存，动态库存与 QoS 关闭。优先比较下一波的响应、完成与拒绝、补池恢复和空闲资源代价；持续场景继续作为容量边界，不将 Warm 的目标设为突破固定机器的持续产能。

先用现有机制验证目标使用场景，不因持续负载分数不领先就先改解释器或增加库存。当前波次未包含受保护核心服务，业务干扰仍需独立对照。

## 已补充：按延迟目标定位容量边界

已补充独立 capacity 阶梯扫描：同时记录提供、交付、按期成功、排队、创建/执行占用以及 CPU 节流与 PSI；目标越界停止加压，基础设施或内存异常终止发起。默认运行不会附带容量扫描。执行/创建可选上限扩大为 8/4，总实例上限仍为 8，服务默认配置与 CPU/内存预算保持原值。

先以固定配额和工作负载找最后达标／首个失败区间，再只在区间附近做更长、重复的确认。需要调参时分别扫描执行和创建并发，避免同时改变多个因素；保留波次场景作为 Warm 的交互收益标准。书中依据、使用入口和实测结果分别见 [理论](performance-theory.md#capacity)、[容量扫描](warm-pool.md#容量扫描寻找可用边界)和[验收](validation.md)。尚未测出裸机上限，也未选出最优并发参数。

## 已完成：区分瓶颈，补齐实例 CPU 配置

1. 已完成现有 capacity 入口的五组对照：相同 10 req/s、每路 200 请求；父组 4 CPU 时执行并发 2/4/8，执行并发 8 时父组 2/3/4 CPU，复用交点。创建并发 4、单实例 1 CPU、总容量 8、内存与队列保持一致；2,000 请求与回收核对通过，只有单次探索。4槽/4CPU 比 8槽/4CPU 按期交付更好，但没有组合满足本次 95% 目标，不改服务默认值或宣称最优配置。对照父组参数仅能收紧既有 4 CPU 上限。
2. 已增加服务端 `-sandbox-cpu-milli`／`AGENTBOX_SANDBOX_CPU_MILLI`，默认 1000（1 CPU）、范围 50～4000，Cold/Warm 创建与补池共用。status 报告配置值；CLI、unit、解析、smoke 和内核实际值检查接通。父组默认和请求接口保持原值，资源仍不由任务任意指定。
3. 根据交付、按期成功、生命周期阶段耗时与节流解释对照结果；不足以辨别的原因保留为假设，不通过继续增加槽位或开启新控制器代替定位。维持正常配置默认值，性能建议限定到测量的工作负载与配额。

## 已完成：补池条件与 Core 对照

已增加可选 slots/idle 补池规则与精确启动计数。idle 在任何前台生命周期在途时暂停新后台预留，按需创建仍有界可用，不取消已开始创建。默认 slots 不变；CLI、systemd、status、单元与真实执行/生命周期接通。

相同波次、CPU/并发下完成两轮反向排序的 Core-only／Cold／Warm-slots／Warm-idle，含 25,920 个 Core 和 300 个沙箱请求。两轮 idle 相对 slots 降低 Core P99、减少拒绝并增加沙箱完成，但仍未守住 50ms 目标，沙箱 P95 也未全面改善。详见[验收](validation.md)，不将实验策略提升为通用默认。

## 已完成：预算余量与 PSI 方案验收

父组 CPU 预算已接入 CLI/systemd，AIMD 最大值不得越界；新增只控制补池的 PSI 作用域，不影响准入、CPU 或在途任务。六方案两轮反向对照完成，38,880 个 Core、500 个沙箱请求与回收核对通过；真实 PSI 高低压、缺测保持、部署与完整回归通过。

1 CPU＋PSI 仅补池在三个窗口中两轮都达到预先目标，Core 共 6,480 请求全部按期成功，沙箱完成 33/36（每轮50）。但门控未触发，不能归因为动态收益；1 CPU＋idle 仅一轮全部达标，PSI 2 CPU 和 AIMD 组合均未达标。组合有真实调额，仍未优于保守预算。详见[验收](validation.md)。

## 当前重点：单机收尾与配置建议

本阶段已有明确条件、达标运行点、任务代价、失败反例及复现入口，可进入收尾，不继续在同一轨迹上调参。配置建议须同时限定共享 2 CPU、Core 60 req/s 固定工作量、并发/库存/队列，以及沙箱拒绝与等待；不承诺任意负载或硬实时 SLO。父组与补池策略可正式部署，默认不自动切换。

若继续动态借用，优先验证已有的保守 base CPU＋真实业务健康窗口，从余量借用并撤回，而非从上界启动、只靠 PSI。该可选模式只有功能验收，本轮组合 BaseCPU=0，不能挪用为其收益证明。动态库存、任务规格和物理跨机不作为本轮收尾前置。

只有出现实际混合任务需求时，再实现服务端 small/standard 等有限规格及 Warm 匹配、预算和排队公平。kind 多节点仍是后续功能模拟，不能替代本机瓶颈解释。

## 后续：kind 多节点接入与故障模拟

没有第二台物理宿主机，使用独立 kind 集群模拟两个 Worker，保留现有集群。先验证固定目标调用，再增加路由，避免同时改变接入与调度语义。

1. 为两个 Worker 准备独立状态目录、Unix socket、cgroup 资源子树和普通用户入口，固定运行时依赖与委派配置。
2. 先用受控端口转发接入指定 Worker，验证执行归属、取消、断线和回收，不直接暴露 root daemon。
3. 再加入最小节点配置、健康状态与过期过滤，按归一化在途负载选择 Worker；上报只是提示，最终准入仍由 Worker 原子完成。
4. 覆盖满载、节点停止、入口重连和不确定结果。禁止不确定执行跨节点自动重放；模型不选择任意宿主路径或网络地址。

完成标准：两节点分别执行并清理成功，故障节点不再接新任务，结果带 Worker 归属，同一 MCP/Agent 工具链可调用。kind 共享宿主 CPU、内存和 PSI，只验证分布式功能，不代表物理跨机隔离或性能改善。

## 验证边界与后续工作

- 修改相关代码后先跑单元/race；收尾运行 make check/build。传输、权限或生命周期改动增加一条短真实验证。
- API 可按验证需要使用，保留轮数/超时和结果不确定时停止的语义，不把成本低解释为允许无界循环。
- 正常磁盘 create/delete 超时仍是已知问题，相关场景复现时按阶段日志定位；不作为全部开发前统一的大规模实验门槛。
- 长时间供给、动态 QoS 对照与参数寻优按性能报告需要安排。解释器预加载、动态执行并发、内存压力准入、多租户公平和独立结果查询另行实现。
