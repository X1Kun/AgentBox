# AgentBox 面试讲解

更新：2026-10-21。本文把已实现机制、已验证结果和待验证收益分开。历史性能数据及环境见 [验收记录](validation.md)；不把旧版本实验当作本轮实现的性能结论。

## 30 秒开场

> AgentBox 是我用 Go、gVisor 和 cgroups v2 实现的单机 Python 沙箱执行引擎，面向 AI Agent 执行不可信代码。它采用普通用户 Gateway 与特权 Daemon 分离、一次性沙箱和有界准入，降低跨任务状态残留与资源争抢风险。历史实验中，预热命中降低了启动准备延迟，静态 CPU 限额改善了同机核心服务尾延迟；PSI 驱动的动态控制作为可选策略单独验证。项目也通过 MCP 接入真实 DeepSeek，跑通代码报错后的修正执行。

这段开场不承诺零干扰、杜绝逃逸或动态策略必然优于静态策略。被问性能时，再展开场景和数字。

## 项目为什么存在

AI Agent 会产生需要执行的代码。执行平台需要同时处理代码隔离、资源上限、启动等待、取消、失败回收和工具结果语义。AgentBox 关注本机执行与同机业务保护，并提供普通用户可用的入口。

没有实测 E2B、Modal、Lambda 或 Firecracker，所以不宣称它们普遍慢于 300ms、价格昂贵或一定要求数据出境。普通容器也可以配置 cgroups；项目的工作是把隔离、限制、反馈控制和回收组织成一个受约束的执行服务。

## 实际调用链

```text
DeepSeek API（HTTPS，Tool Calls）
          ↕
agentbox-agent（普通用户，持有模型 API key，控制工具调用轮数）
          ↕ MCP / JSON-RPC over stdio
agentbox-mcp（普通用户，execute_python + get_status）
          ↕ Loopback HTTP + Gateway token
agentbox-gateway（普通用户，鉴权、输入边界、在途并发上限）
          ↕ Unix HTTP + Daemon token（配对部署 socket 0660）
agentboxd（root，独占状态目录，操作委派 cgroup 子树）
          ├─ 统一 FIFO 准入与有界创建器
          │    ├─ Cold：不维持待命库存，按需创建
          │    └─ Warm：优先使用 READY，缺货时在同一预算内按需创建
          ├─ gVisor / runsc + 每实例资源限制
          ├─ 可选 PSI 观测、CPU AIMD 与压力门控
          └─ 执行结束、超时或取消 → 销毁与回收确认
```

统一创建器已通过一次同预算 KVM 短测；再加入补池退让后，创建并发均为 2 时，持续 10 req/s 场景 Cold 完成 52/60、Warm 完成 51/60；库存充足时 P50 为 272.05/147.09ms。它保留命中收益，但没有证明持续吞吐领先。不能套用旧的 49/60 与 34/60 数据证明本轮收益。此前 Cold 无 FIFO、Warm 只靠补池的实现应作为历史复盘说明。

模型不会直接讲 MCP；Agent 程序把模型 Tool Calls 转成 MCP 调用。API key 只由 Agent 持有，不传入 MCP、Gateway 或任务环境。工具输出的模型侧截断由 Agent 负责。

Gateway 有在途并发限制，不等于按用户限速或防暴力破解；它不维护执行 FIFO，执行排队属于 Daemon。当前 Gateway 固定连接一个本机 Daemon，没有多 Worker 路由。Daemon 本身仍支持 loopback TCP；配对部署使用 Unix socket。

## 三个值得展开的设计

### 一次性隔离与启动等待

每任务领取全新实例，执行后进入销毁状态，不回到 READY。只读 rootfs、UID/GID 1000、空 capabilities、NoNewPrivileges、禁网和资源限制共同降低风险，不能构成“绝对安全”的证明。

预热提前创建运行时并启动待命 init，使用附着式 `runsc exec` 执行用户任务。用户 Python 解释器仍会新启动；rootfs 是部署时准备的共享只读依赖，不在每个请求里解压。

本轮将 Cold/Warm 放入相同的创建并发、执行并发、总实例数和 FIFO 预算。Warm 命中时原子取得实例与执行名额；缺货时原子预留创建、执行和总容量，随后在锁外创建。后台补池在执行槽饱和或存在排队请求时退让；已开始的创建允许完成。取消或部分创建失败也必须保留清理责任。

历史数据：库存充足时，Setup P50 为 72.57→10.24ms，成功请求端到端 P50 为 287.78→156.40ms。这个收益不等于持续吞吐提升，也不代表解释器已经完成预加载。

### 静态资源保护与可选动态控制

cgroups v2 提供内核侧资源约束。CPU 配额表示时间带宽，不表示绑定或独占物理核心；内存预算必须给管理进程、共享依赖和宿主业务留余量。

PSI 用累计 stall 时间差除以采样间隔，估计该窗口的等待比例。默认采样间隔为 100ms，CPU 控制动作以秒级确认与冷却执行，不能说“毫秒级让出全部算力”。

CPU 策略采用非对称 AIMD：持续高压时乘法降额，持续低压且沙箱存在带宽需求时加法恢复；滞回、动作间隔与失效样本处理用于降低误动作。它不能保证不振荡，也不保证核心业务 SLO。准入和补池门控由压力状态机执行，不是 AIMD 同时调整所有旋钮。

历史静态对照：在外层 2 CPU / 5GiB 容器内，把沙箱父组配额从 4 CPU 降至 1 CPU，三轮核心服务 P99 从 80.64～94.52ms 降至 21.77～23.77ms；无沙箱基线为 17.15～21.44ms。沙箱完成率同时从约 0.53～0.57/s 降至 0.37/s。负载是固定工作量计算，不是该结论所声称的无限死循环。

这是静态隔离的收益。动态策略要另外回答：在低压→高压→低压负载中，是否能在同等核心业务保护下完成更多任务，或更快恢复。本轮单次低压→高压→低压对照确实观察到 AIMD 调节：配额从 2 降至 1.024，再回到 2 CPU。高负载核心 P99 为固定 1 CPU 的 73.76ms、固定 2 CPU 的 135.43ms、动态方案的 93.69ms；45 秒沙箱完成数分别为 16、25、26。动态方案保护弱于保守静态方案，也没有满足预设 50ms SLO。这个结果展示原 PSI-only 策略的取舍，不能作为“全面优于静态”或统计显著收益；保持默认关闭。随后补的无沙箱高负载基线为 900/900 成功、P99 16.88ms，说明该次环境能满足 50ms。新增的可选业务健康约束会限制恢复并撤回借用额度，但目前只验证了机制，未证明业务性能收益。详见 [本轮完整边界与拒绝计数](validation.md)。

### 最小权限与确定性回收

普通用户 Gateway 缩小网络入口的特权范围；Daemon 仍负责校验授权与执行参数。网络入口分离不能消除 root Daemon 自身的解析和运行时风险。

启动会先完成一次可信 Python 创建、执行和销毁探测，通过后才开放 readiness。失败不隐式重试；该检查不保证之后的存储永不抖动。

清理先尝试 `runsc delete --force`，再 `cgroup.kill` 并等待空组、移除 cgroup，最后移除 bundle。运行时删除和兜底空组等待有独立预算。清理不能确认时保留记录并停止新准入，不把不确定结果标成成功。

当前任务响应等待回收确认。空闲库存回收有并行机制，但不能把整个系统说成“任务完成即异步回收并返回”。`populated=0` 与目录删除也不意味着全部内核对象已经同步释放。

## 四个可以讲的复盘

### 短任务退出状态

早期直接让短任务充当 init，执行结束与后续状态获取存在竞态。现在使用待命 init 维持运行时，任务通过附着式 exec 执行，结合任务 PID 文件与退出码区分用户失败和运行时失败。相关退出码、超时和取消用例已回归。

不要说“systemd 瞬间收割导致所有问题”或“准确率永久 100%”。PID 文件也不是 PID 锁文件。

### Warm 34/60，Cold 49/60

历史 10 req/s、约 6 秒短测里，Warm 完成 34 个、Cold 完成 49 个。Warm 创建并发为 1，Cold 可随 4 个执行名额并行创建；两者同样每任务销毁。因此这组结果暴露了库存与供给能力的区别，却不能证明一次性隔离不可行，也不能归因于尚未测量的锁竞争。

本轮改进是统一创建与准入预算，并让 Warm 缺货能按需创建；统一供给后的短测为 Cold 52/60、Warm 49/60，补池退让后另一轮为 52/60、51/60。新旧环境和预算不完全相同，不能把 Warm 从历史 34 到后续 49/51 全部算成代码优化收益。不要用调低 Cold 资源后的相对领先，隐去绝对完成量或旧基线。

### 动态库存的错误信号

旧策略把排队当成缺库存，又依赖“整池长期空闲”缩容，分别导致槽位不足时误扩容、低频请求不断推迟缩容。

v2 区分队首等待执行槽、库存或两者；以真实库存等待作为扩容信号，用一段时间内的库存低水位生成缩容建议。单调递减队列保留稳定窗口内的建议最大值，因建议为 1～8 的整数，最多保留 8 项，操作摊还 O(1)。

单调队列只是缩容稳定机制，不是预测器。新调度路径中的即时按需创建不再属于“排队等库存”，相关信号不能把所有缺货都算作扩容需求。真实清理耗时、压力门控和采样中断也意味着“30 秒后必然释放”并非保证。

### 普通磁盘路径超时

历史测试在普通磁盘依赖上出现 create/delete 超时；迁入 tmpfs 后部分验收通过，但这没有定位或修复原有存储问题。

本轮新增失败前有界快照，已在一次普通磁盘 KVM create 超时中记录到：runsc CLI 处于 D 状态，栈为 `filemap_fault → folio_wait_bit_common`；对应沙箱 cgroup 尚未 populated，memory.current 为 0，宿主 I/O PSI 较高。依赖路径位于 ext4。

这证明该次 create 阻塞发生于文件缺页等待阶段，不能推断所有历史超时同因，更不能声称已经定位到 ext4 日志锁、Gofer 同步 I/O 或 cgroup 销毁回写。tmpfs 是有成本的测试条件；继续定位底层存储时应保留证据，而不是反复延长超时。

## 常见追问

**为什么选 gVisor？**

需要执行较完整的 Python/Linux 用户态程序，又希望减少不可信代码直接接触宿主系统调用接口的范围。gVisor 的 Sentry 提供用户态内核实现，适合本项目的隔离模型。没有做同配置 Docker/Firecracker 比较，所以不承诺启动、内存或安全性全面领先，也不说 Firecracker 必须配置虚拟网卡。

**清空目录为什么不够？**

目录清理不覆盖后台进程、解释器内存、共享对象等状态。跨任务采用全新实例，能减少证明“复用环境已彻底恢复”的负担。同一可信会话复用可以作为另一种产品模式，但会改变隔离单位，需要另行设计。

**静态配额够用，为什么要 AIMD？**

先承认静态方案简单且已有效。动态控制的动机是在业务负载变化时利用剩余 CPU，而不是宣称固定配额无用。对照要同时报告核心业务 SLO、沙箱完成量、拒绝和恢复时间；没有测出优势就不默认开启。

**崩溃如何恢复？**

运行时状态目录有独占 flock；bundle 目录承担创建意图记录，重启时先扫描并对已记录资源清理，再进入就绪状态。systemd 对托管进程提供兜底终止。没有独立的 `intent` 标记文件，也没有承诺自动找回所有未记录资源或处理所有主机掉电损坏；清理失败需要运维处理。

**模型错误修正验证到了什么？**

真实 `deepseek-flash` 联调进行了 3 次模型请求、2 次真实执行：第一次出现 ZeroDivisionError，随后生成新代码并得到 42，均核对回收。不是 DeepSeek-V3/R1 的实测，也不是任意错误都会自愈。结果不确定或回收未确认时禁止自动重放。

## 诚实的边界

这是完成多项真实运行时验证的单机工程项目，尚不能宣称生产就绪或经过完整安全审计。默认 Cold，动态 QoS 和动态库存关闭。普通磁盘稳定性尚有缺口，跨物理宿主机调度尚未验收。

当前先收敛清理、预算、统一供给与动态收益对照。之后才讨论多 Worker 接入、会话复用或干净模板恢复。gVisor checkpoint/restore 不等于廉价 Fork；“唤醒 10ms”没有实测支持。OverlayFS、loop device 也不自动提供磁盘空间与 I/O 带宽配额，不能直接当作已确定的替代方案。
